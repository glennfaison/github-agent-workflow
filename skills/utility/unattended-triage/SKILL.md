# Unattended triage

The judgment half of triage. Given one issue, decide where it belongs and write the comment that goes with the decision. The caller owns everything that touches GitHub: claiming, labels, posting. This skill only reads, thinks and writes text.

Every comment this skill produces **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Roles

Two **category** roles: `bug` (something is broken) and `enhancement` (a new feature or improvement).

Five **state** roles, from `agent-workflow-protocol`'s `references/labels.md`: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. This skill only ever recommends one of three: `needs-info`, `ready-for-agent`, `ready-for-human`.

## Process

1. **Gather context.** Read the whole issue: body, comments, labels, author, dates. Parse any earlier triage notes so you never re-ask a resolved question. Explore the codebase using the project's domain glossary (read `GLOSSARY.md` if it exists) and respect ADRs in the area. Run two checks:
   - **Redundancy.** Search for an existing implementation of the requested behaviour by domain concept, not just the request's wording, and note where you looked. If it exists, the issue is already implemented.
   - **Prior rejection.** Read `.out-of-scope/*.md` (see [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)) and note any that resembles this request.
2. **Verify the claim** before any questions. For a bug, reproduce it from the reporter's steps. Report what happened: confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed reproduction makes a much stronger brief.
3. **Question what is still open.** If the request needs fleshing out, call the Skill tool with `unattended-grilling` and put the round it returns into the comment. Do not wait for answers.
4. **Decide.**
   - `needs-info`: any question is open, or a required section of the issue is missing and cannot be inferred.
   - `ready-for-agent`: an agent can implement it from the issue, its comments, any images, the ADRs and the codebase, with nothing left to decide.
   - `ready-for-human`: a human is needed (product decision, access, judgment, manual testing). Also use this when you would recommend closing the issue as `wontfix`, either because it is already implemented or because it was rejected before. Say which, and why.
5. **Write the comment** for that state:
   - `ready-for-agent`: an **Agent Brief**, as [AGENT-BRIEF.md](AGENT-BRIEF.md) describes. The brief is the contract: the original discussion is context.
   - `ready-for-human`: the same structure, plus why it cannot be delegated. For a recommended `wontfix`, give the recommendation and its reason instead, and, for a rejected enhancement, the proposed `.out-of-scope/` entry.
   - `needs-info`: **Triage Notes**, below.

## Result

Return all of:

- the category and the state,
- the full outcome comment, disclaimer first,
- any proposed repository changes (a `GLOSSARY.md` term, an ADR, an `.out-of-scope/` file) as text for the comment. Do not make them.

## Triage Notes template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved so far under "established", so the work is not lost. Questions must be specific and actionable.

## Never

- Change the repository: no commits, no branches, no edits to `GLOSSARY.md`, ADRs or `.out-of-scope/`.
- Close an issue or recommend closing it as anything other than `ready-for-human` with a reason.
- Apply labels or post comments. The caller does.
- Assume an answer to a question you have not been given.
